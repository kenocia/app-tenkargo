Equipo

Quién hace qué.

División de responsabilidades para todo el proyecto. Coordinación entre ambos vía Odoo (API) como contrato de datos.

ROBERTO
Diseño (UX/UI) + App móvil (Flutter)
  • Diseño de pantallas: splash/login, discover (mapa/lista/filtros), detalle de comercio/oferta, checkout/pago, mis reservas, pickup, favoritos, perfil, notificaciones
  • Implementación Flutter (iOS + Android, un solo codebase)
  • Integración con la API REST que expone Gilberto (autenticación por token)
  • Notificaciones push (FCM / APNs)
  • Código de recolección (QR o PIN de un solo uso) en cliente
  • Manejo de estado de reserva en tiempo real desde la app
  • Preparación y publicación en App Store y Google Play
  • Sistema de diseño: tokens de color/tipografía a definir una vez el cliente envíe sus assets (ver Pendientes)
GILBERTO
Backend / Odoo + APIs + Infraestructura + Seguridad
  • Modelos Odoo: comercio, sucursal, oferta, disponibilidad, reserva, pago, recolección, rating
  • Multi-comercio con seguridad por comercio/sucursal (record rules)
  • Control de concurrencia en reservas (bloqueo/hold temporal — evitar sobreventa)
  • API REST sobre Odoo (controllers), autenticación por token
  • Integración PowerTranz (BAC): captura de pago, webhook, idempotencia
  • Reporte de liquidación semi-manual por comercio y período
  • Tablero de indicadores (KPI) para comercio y administración
  • Ranking de comercios y de clientes (consultas agregadas)
  • Infraestructura: servidores prod/staging, Redis, object storage, backups, NGINX
  • Seguridad: HTTPS/SSL, auditoría de cambios de estado, control de acceso por rol
Punto de sincronización: Roberto no debe mockear datos por su cuenta más allá de la etapa inicial de maquetado — la API de Gilberto es la única fuente de verdad para reservas, pagos y estados. Cualquier cambio en el modelo de datos se coordina antes de tocar la app.

Riesgos técnicos

Lo que no se puede pasar por alto.

RiesgoImpactoMitigación
Sobreventa de ofertasMuy altoBloqueo a nivel de fila + hold temporal (Gilberto)
Pago confirmado, reserva fallidaMuy altoIdempotencia por intento de pago (Gilberto)
Fraude en pickupAltoCódigo QR/PIN de un solo uso, con expiración (ambos)
Diferencias contablesMuy altoTodo evento financiero auditado, sin ediciones manuales (Gilberto)
Rechazo en revisión de tiendasMedioSeguir guidelines de Apple/Google desde el primer build (Roberto)
Pendiente de recibir

Lo que falta del lado del cliente.

No bloquea el arranque técnico, pero sí afecta directamente el trabajo de Roberto en diseño.

🎨
Assets de marca del cliente — pendientes de aprobación

Una vez el cliente apruebe la propuesta, enviará diseños de referencia, paleta de colores y estructuras gráficas a considerar para la identidad visual de la app. Hasta entonces, Roberto trabaja con el sistema de diseño placeholder (tokens de Kenocia) para no detener el avance de UI/UX y maquetado — el remplazo de marca al final es principalmente un cambio de tokens (color, tipografía, logo), no de estructura.
